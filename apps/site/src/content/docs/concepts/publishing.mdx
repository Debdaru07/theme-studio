## Contrast checks

Every resolved theme gets a contrast report (WCAG 2.1 relative luminance), checked in **both** light and dark mode.

| Pair (foreground / background) | Minimum | Effect when failing |
| --- | --- | --- |
| `onSurface` / `surface` | 4.5:1 | **Blocks publish** |
| `onSurface` / `background` | 4.5:1 | **Blocks publish** |
| `onPrimary` / `primary`, `onSecondary` / `secondary`, `onAccent` / `accent` | 4.5:1 | **Blocks publish** |
| `on<Role>Container` / `<role>Container` for every brand and semantic role | 4.5:1 | Warning |
| `onSuccess` / `success`, `onWarning` / `warning`, `onError` / `error`, `onInfo` / `info` | 4.5:1 | Warning |
| `onSurface` / `surfaceContainerHigh` | 4.5:1 | Warning |
| `onSurfaceMuted` / `surface`, `onSurfaceMuted` / `background` | 4.5:1 | Warning |
| `outline` / `surface` | 3:1 | Warning |
| `focusRing` / `background` | 3:1 | Warning |

The core pairs are where text sits on the brand and on the page. Theme Studio shows all failures inline while
you edit; only core pairs stop the Publish button. The API enforces the same gate: a publish that fails it returns
`422` with the contrast report.

## Lifecycle

<Steps>

1. **Draft.** Edits in Theme Studio autosave to a draft (`PUT …/theme/draft`). Drafts are private to editors;
   apps never see them.
2. **Preview.** The live preview resolves the draft on top of the published base in the browser, using the same
   resolver and the same React SDK apps use.
3. **Publish.** `POST …/theme/publish` (with an optional note) resolves the draft, validates it, checks contrast and
   stores an **immutable version**: the layer, the resolved JSON and its hash. `GET /v1/theme` serves it
   immediately with a new `ETag`.
4. **Rollback.** `POST …/theme/versions/:version/rollback` copies an old version's layer into the draft and
   publishes it as a **new** version (note: `Rollback to vN`). History is never rewritten.

</Steps>

## Publishing a base theme rebases clients

Client themes are overrides on top of the agency's base. When a tenant admin publishes a new base theme, the API
re-resolves **every client that has a published theme**: it takes the client's current published layer, resolves
it on the new base, and publishes it as a new client version noted `Rebased on base theme vN`. Live apps of every
rebased client update at once; others pick it up on their next sync.

A client whose layer would fail the core contrast checks on the new base is **skipped** (its previous version stays
live). The publish response lists `rebased` and `skipped` clients with the reason.

## How apps receive a publish

With **live updates** on, an open app re-skins within about a second of a publish, with no reload. The SDK holds a
Server-Sent Events connection to [`GET /v1/theme/events`](/api/#get-v1themeevents) only while the tab is visible
or the app is in the foreground, and re-checks the theme whenever it becomes visible or regains focus. A base theme
publish notifies every client it rebases; a rollback notifies like any other publish.

| SDK | Turn it on | Without it |
| --- | --- | --- |
| Web | `client.watch()` (returns a stop function) | `client.load()` once; call `client.refresh()` yourself |
| React | `<ThemeProvider client={client} live>` | Loads on mount |
| React Native | `<ThemeProvider client={client} live={{ eventSource }}>` with an EventSource polyfill | Loads on mount |
| Flutter | `DynamicThemeApp(live: true)` or `DynamicThemeBuilder(live: true)` | Refreshes on launch, on resume and on `pollInterval` |

<Aside type="note" title="Free hosting">
The hosted API runs on a free Render instance that sleeps when idle. Connections close while apps are in the
background so the API can still sleep; waking it can take up to a minute, and the SDKs keep
showing the cached theme meanwhile.
</Aside>
